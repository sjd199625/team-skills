# 变更总结

只根据真实改动写，不根据用户口述补全。

## 获取上下文

1. 先确认基线分支。通常使用 `git merge-base HEAD origin/main`；基线不明确时再询问用户，不要猜。
2. 读取 `git diff <base>...HEAD` 和必要的提交信息。
3. 如果改动涉及多个模块，按行为分组阅读，不要只按文件名罗列。

## 输出

默认输出四部分，没有内容的可以省略：

- **改了什么**：按用户可见行为或系统行为分组，说明主要变化。
- **为什么改**：只写能从代码、提交信息或需求中确认的动机；不确定就标注“未确认”。
- **怎么验证**：列出实际执行过的测试、构建或手工验证及结果。
- **风险与回滚**：仅在有兼容性、数据、配置或发布风险时说明。

如果用户要求 PR 描述，使用简洁的 Markdown；如果要求提交说明，输出一行标题和必要的正文。

## 约束

- 没有运行测试就写“未运行”，不要声称通过。
- 不虚构工单号、影响范围、性能数据或用户价值。
- 不自动 commit、push、创建 PR 或修改代码，除非用户明确要求。
- 用户只给了模糊描述时，先看 diff；不要替用户编造变更原因。
