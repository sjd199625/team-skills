# 快车道交付

默认用于“需求和目标分支已经明确，用户要尽快把页面做出来”的场景。默认只维护三份产物，不再按八份文档拆解。

## 核心原则

- 开始开发前只保留一份一页技术设计。
- 不在页面能跑之前批量生成需求、测试计划和交付总结。
- 不重复读取同一目录的全部文档；只读当前阶段的输入和最近一份测试报告。
- 每次编辑只跑与改动相关的检查；稳定后再跑一次构建。
- 真实接口、后端业务和飞书发布按需执行，不让它们阻塞页面交付。

## 第 0 步：一次预检

在 skill 目录执行：

```bash
python3 scripts/project_context.py \
  --repo '<repo>' \
  --feature '<feature>'
```

确认：

- 当前仓库、分支、提交和工作区改动；
- 项目脚本和真实页面目录；
- 当前 feature 是否已有文档；
- 是否存在同模块的页面可以复用。

再读：

1. `references/project-profile.local.md`（不存在时读 `project-profile.md` 模板）
2. `docs/<feature>/01-frontend-tech-design.md`（如果已存在）
3. 目标目录最近的一个同类页面
4. 只与当前需求相关的 API、路由和样式文件

不要先读完整八份历史文件，也不要重新抓取没有变化的飞书。

## 第 1 步：一页技术设计

只写下面 7 块，控制在半页到一页：

```text
页面和路由
复用的现有组件
新增文件和职责
接口/mock 的输入输出
正常/空/异常/重试
本次不做什么
验证命令和页面
```

如果已有完整技术文档，只补一个“本次实现增量”，不要重写整份文档。

## 第 2 步：按同类页面实现

优先顺序：

1. 复用同模块页面骨架；
2. 复用项目已有的表格、弹窗、Bridge 和请求封装；
3. 只新增本次真正需要的页面内组件；
4. 最后才把复杂流程抽到 `model.ts` 或通用组件。

可以按同类页面参考：

- 移动 H5：`src/pages/<Feature>/` 中的纯函数、mock、页面配置和组件拆分。
- PC 后台：`src/pages/<Domain>/<Page>/` 和现有表格/表单组件的用法。

不要复制整个业务目录，只复制与当前问题相同的模式。

## 第 3 步：分层验证

测试前先读 `project-profile.local.md` 的测试入口、登录态和 mock 开关；不存在时读模板。登录态拿不到时写阻塞，不要跳过核心入口。

每次稳定一小块：

- 纯状态、字段归一化、mock 分支：跑对应逻辑断言；
- 页面可访问后：先跑 1 条正向主流程；
- 正向通过后：再补空、异常、重试和权限；
- 页面结构稳定后：跑一次项目 build；
- 交付前：再跑目标测试和完整构建。

不要每改一行就全量 build，也不要用构建替代浏览器验收。

## 第 4 步：按阶段补文档

| 时间点 | 必须落盘 |
| --- | --- |
| 开始写代码前 | `01-frontend-tech-design.md` 的本次增量 |
| 页面完成后 | `01-frontend-tech-design.md` 的实现记录 |
| 测试完成后 | `02-test-cases-results.md` |
| 真正联调时 | 可选的 `03-backend-business.md` |

已有文档只更新发生变化的部分，不重新生成整份。测试失败和阻塞必须保留，不为了快而省略。

## 何时追加第三份文档

- 需求本身仍有影响实现的未决问题。
- 需要真实后端、设备、权限或发布。
- 当前分支和需求范围无法确认。

只有这时才生成 `03-backend-business.md`；没有后端输入时不要生成空文档。
